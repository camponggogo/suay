# BitTorrent-style distribution: will it help SUAY?

**เอกสารตัดสินใจ · 2026-10-21 · อ้างอิงผลวัดจาก `report/REPORT.md`**

## สรุปคำตอบ (อ่านบรรทัดเดียว)

**ช่วย — แต่ไม่ใช่ในจุดที่คนมักคิด** ไอเดียแบบ BitTorrent ให้ผลชัดที่ชั้น *แจกจ่าย artifact* (โมเดล/block) และชั้น *pull-based scheduling* แต่ถ้าเอาไปใช้ "กระจายการประมวลผลต่อ token" ข้าม 50 เครื่องตอนนี้ **จะช้ากว่าเดิม** เพราะคอขวดที่วัดได้คือ gateway ตัวเดียว ไม่ใช่เครื่องปลายทาง

| ชั้นของไอเดีย BitTorrent | ช่วยไหม | เหตุผลจากตัวเลขที่วัดได้ |
|---|---|---|
| **A. Swarm แจกไฟล์โมเดล** (chunk hash, rarest-first) | **ช่วยมาก** | 50 เครื่องดาวน์โหลดเอง = 50 × 16 GB ≈ 800 GB ต่อ cold start; swarm ลดเหลือ ~16 GB + overhead |
| **B. Pull-based work stealing** (โหนดมาดึงงานเอง) | **ช่วย** | ลบจุด serialize ที่ทำให้ ceiling 10.18 rps; กระจายงานได้โดยไม่มี dispatcher กลาง |
| **C. Pipeline/tensor sharding ต่อ token ข้าม 50 เครื่อง** | **ไม่ช่วย (แย่ลง)** | S* = 3–10 เท่านั้น; 50 stage = overhead 150 ms/token ขณะที่ compute เหลือ 0.6 ms |
| **D. Tit-for-tat / reciprocity** | **ไม่ช่วย** | องค์กรเดียวไม่ต้องแลกแต้ม; ทำให้งานตกเพราะเครื่องช้าโดนตัดสิทธิ์ |

---

## 1. คอขวดที่วัดได้ (ย้ำเพื่อกันเข้าใจผิด)

จาก 966 คำขอ, 10 ระดับ concurrency:

- throughput  asymptote **10.18 req/s** (peak 10.87), knee **C=2**
- service floor **174 ms**; ที่ C=50 เวลา **96.5 %** เป็น queueing (amplification 28.95×)
- **dispatch ไปเครื่องจริง: 31–45 ms และไม่โตตามโหลด** → เครื่อง 50 ตัวไม่ใช่คอขวด
- fairness 19–20 หน่วย/เครื่อง (CV 0.024) → ภาระกระจายสม่ำเสมออยู่แล้ว
- payload **0.034 Mbit/s** = 0.003 % ของ 1 GbE → เน็ตยังว่างมาก
- heartbeat พื้นหลัง **24.6/s** = 2.4 เท่าของ throughput inference

แปลว่า: การกระจาย "การคำนวณ" ออกไปอีก **ไม่แตะคอขวด** เพราะคอขวดคือกระบวนการเดียวที่รับ request, ตรวจ token, เขียน SQLite และเรียก HTTP ออกไป

## 2. แต่ละชั้นควรทำ/ไม่ควรทำ

### A. Swarm สำหรับ artifact — คุ้มที่สุด และวัดผลได้ง่าย

ปัจจุบันแต่ละเครื่องดึง block/weights จาก Hugging Face เอง ต้นทุน cold start = O(n) ต่อจำนวนเครื่อง

- 50 เครื่อง × โมเดล 16 GB = **800 GB** egress ถ้าดึงแยกกัน
- swarm (chunk 4–16 MB + SHA-256 ต่อ chunk + rarest-first) → ดึงจากภายนอก ~16 GB ที่เหลือแลกกันในวงแลน
- LAN 1 GbE รับ 16 GB ได้ใน ~130 วินาที (ทางทฤษฎี) เทียบกับ 50 เครื่องแย่งลิงก์อินเทอร์เน็ตเดียวกัน

**สิ่งที่ต้องมี:** manifest + hash ต่อ chunk, ผู้ให้บริการ chunk ตรวจ hash ก่อนเชื่อ, resume ได้, และ ***ไม่*** ใช้ tit-for-tat กับเครื่องในองค์กร (ทุกเครื่องเป็นเจ้าของเดียวกัน) — ใช้แค่ "ขอจากใครมีก่อน" + rate limit

### B. Pull-based work stealing — เปลี่ยนจาก "hub ยิงงาน" เป็น "โหนดมางาน"

ตอนนี้ hub เป็นผู้ dispatch (เพิ่ม hop หนึ่งครั้งในทุกคำขอ) ถ้าเปลี่ยนเป็นคิวกลางที่โหนดดึงเอง (HTTP long-poll หรือ gRPC stream) จะได้:

- hub ไม่ต้องรอ RTT ของโหนดใน hot path → service floor ลดลง
- scale ได้ด้วยการเพิ่ม worker process ของ hub (แต่ละตัวแชร์คิว)
- โหนดช้าไม่บล็อกงาน (ดึงชิ้นถัดไปเมื่อพร้อม) — ตรงกับจิตวิญญาณ BitTorrent มากกว่า pipeline

**แต่ต้องระวัง:** งาน inference ของ LLM ต่อคำขอไม่สามารถแบ่งครึ่งให้สองโหนดได้ถ้าไม่ใช้ pipeline; pull-based จึงเหมาะกับ "หลายคำขอพร้อมกัน" (throughput) ไม่ใช่ "คำขอเดียวให้เร็วขึ้น" (latency)

### C. Pipeline ข้าม 50 เครื่อง — ตัวเลขบอกว่าผิด

โมเดลต้นทุน: เวลาต่อ token ≈ `T_compute / S + S × hop`

| compute ต่อ token (เครื่องเดียว) | S* ที่ดีที่สุด | เวลาต่อ token | เทียบไม่แบ่ง |
|---|---|---|---|
| 30 ms (8B บน CPU) | **3** | 19.0 ms | 30 ms |
| 100 ms (8B บน GPU ช้า) | **6** | 34.7 ms | 100 ms |
| 300 ms (70B บน CPU) | **10** | 60.0 ms | 300 ms |

ที่ S = 50: overhead = 50 × 3 ms = **150 ms/token** ขณะที่ compute เหลือ 30/50 = 0.6 ms → แพ้การรันเครื่องเดียว ~5 เท่า

แถมด้วย bandwidth: activation 8 KiB/hop × 100 token × 10 rps = **65.5 Mbit/s** = **1,922 เท่า** ของ traffic ที่วัดได้วันนี้ และคิดเป็น 7 % ของ 1 GbE (ถ้า 50 rps จะเป็น ~33 %) — เน็ตจะกลายเป็นคอขวดใหม่ทันทีที่ scale

**ข้อสรุป:** pipeline ควรใช้เฉพาะเมื่อ "โมเดลใหญ่เกิน RAM ของเครื่องเดียว" และใช้ S* = 3–10 พร้อม replica 2–3 ชุดต่อ stage เพื่อกันเครื่องหลุด — ซึ่งคือสิ่งที่ Petals ทำอยู่แล้ว ไม่ใช่ 50-way sharding

### D. Tit-for-tat — ไม่ช่วย และเสี่ยง

ในองค์กรเดียว ทุกเครื่องเป็นเจ้าของเดียวกัน การให้คะแนน reciprocity จะทำให้เครื่องที่แชร์ CPU กับงานอื่น (และช้าเป็นครั้งคราว) ถูกตัดสิทธิ์ ทั้งที่ไม่มีปัญหาเรื่อง free-rider — ควรใช้ **health-based routing** (ข้ามโหนดที่ stale/โหลดสูง) แทน

## 3. ลำดับที่ควรทำ (เรียงตามผลตอบแทนต่อแรงที่ลง)

| ลำดับ | งาน | ผลที่คาด | วัดด้วยอะไร |
|---|---|---|---|
| **P0** | Gateway: pooled upstream client, token cache 5 s, 2–4 workers + SQLite WAL, ย้าย heartbeat ออกจาก hot path | **3–8×** throughput (จาก 10 → 30–80 rps) | harness เดิม (`loadgen.py`) ที่ C=8/16/32 |
| **P1** | Pull-based work stealing + คิวกลาง | scale ตามจำนวน worker, fairness ยัง CV < 0.1 | E2 ด้านล่าง |
| **P2** | Swarm แจก artifact (chunk + hash + rarest-first) | cold start −70–90 %, egress −~95 % | E3 |
| **P3** | Pipeline เฉพาะโมเดลที่ไม่พอ RAM, S* = 3–10 | ใช้งานได้จริงเมื่อโมเดลโตขึ้น | E4 |

> หมายเหตุ: P0 ให้ผลมากกว่า P3 ทั้งหมดรวมกัน ในสถานะปัจจุบัน

## 5. ความเสี่ยงที่ต้องเขียนในข้อเสนอ

1. **ความน่าเชื่อถือของผลลัพธ์** — โหนดที่รับงานต้องพิสูจน์ว่าไม่ได้ส่ง값เท็จ: hash ของ activation ใช้ไม่ได้ (ค่าลอยตัว), ต้องใช้ redundant computation + spot-check หรือ trusted-node allowlist
2. **ความเป็นส่วนตัว** — activation tensor มีข้อมูลของผู้ใช้ฝังอยู่; การส่งข้ามเครื่องในองค์กรต้องมีนโยบายชัด (ตอนนี้ยังอยู่ใน LAN เดียวกัน)
3. **NAT / firewall / เครื่องปิดกลางวัน** — swarm ต้องมี fallback ไปยัง source กลาง
4. **ความซับซ้อน ops** — chunk store + manifest + version skew ระหว่าง node ที่ shares ต่างกัน
5. **ผลตอบแทนจริง** — ถ้า P0 ทำให้ ceiling เป็น 40 rps แล้ว P3 จะไม่มีความหมายจนกว่าโมเดลจะใหญ่ขึ้นหรือผู้ใช้เพิ่มขึ้น 10 เท่า

## 6. คำตอบสุดท้าย

**BitTorrent ช่วยในฐานะ "วิธีแจกจ่ายของ" และ "วิธีจัดคิวงาน" ไม่ใช่ "วิธีแบ่งคำนวณต่อคำขอ"**

- ทำ **P2 (swarm artifact)** แนวคิดนี้คุ้มและวัดผลได้ใน 1–2 สัปดาห์
- ทำ **P1 (pull-based)** จะปลดล็อกการ scale ที่ติดอยู่ที่ dispatcher
- **อย่าทำ** 50-way pipeline ตอนนี้ — โมเดลบอกว่าแพ้เครื่องเดียว และ bandwidth จะกลายเป็นคอขวดใหม่
- ลำดับที่ถูกคือ **P0 → P1 → P2 → (P3 เมื่อจำเป็น)** ไม่ใช่เริ่มจาก P3 เพราะ "ฟังดูกระจาย"
