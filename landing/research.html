RESEARCH NOTE / 2026-10-21

We measured it.
Including what failed.

Fifty ordinary office machines, one 8-vCPU host, 53 containers and a harness that reports medians and p95 instead of anecdotes. This page is the short version; the white paper has the tables, the method and the caveats.

01 / THE SIX NUMBERS THAT MATTER

What the test bed actually does

CONTROL PLANE

22.3 req/s at C=8

24.8 req/s at C=16 with two gateway workers, 0 errors. One worker caps at 15.7 — the limit is per-request loop time, not the network.

NODE PLANE

44 → 161 req/s

Splitting heartbeats out of the gateway raised heartbeat throughput 3.7× (p50 67 → 3.1 ms) and halved single-request latency, 210 → 105 ms.

PREFIX CACHE

157× faster first token

An 8 000-token document with 90 % reuse: TTFT 111.4 s → 0.71 s, 88.2 % of prompt tokens served from cache. p95 does not improve.

EXPERT ROUTING

90.15 % accuracy

6 000 queries, 31.5 µs per routing decision. Eight 1B domain experts fit in 32 machines at 0.64 req/s versus 86 machines for a mixture of experts (10.7×).

MULTI-PORT

26.5–28.8 req/s

Two ports, clients direct, one worker each. A userspace proxy on the same host gives it back (−25 %). One hundred ports buy nothing but 4.4 GiB of memory.

GROWTH LAWS

15.7 req/s ceiling

Whether nodes grow as N+1 or N·log₂N, throughput saturates at the same gateway ceiling; the superlinear law just spends 6–9× more machines and adds dispatch latency.

02 / WHAT THIS IS NOT

Read the caveats with the numbers

01

Mock backend.

These numbers isolate the control plane. With a real 0.5B model a single machine serves 0.14 req/s, so 50 machines deliver about 7 req/s — the gateway ceiling stops mattering.

02

One host, ±15 %.

Fifty-three containers, Docker Desktop and the load generator share 8 vCPUs. Treat single runs as indicative; the repository ships JSON per run so you can see the spread.

03

Office pools are slower, not cheaper.

Measured generation is 11.6× slower per stream than the median cloud endpoint, and $0.29–2.86 per million output tokens. The case for SUAY is residency, offline operation and control.

03 / NEGATIVE RESULTS

What we tried and retired

50-way pipeline sharding (≤1.3×, worse at 50 chunks) · PostgreSQL on a split schema (4.5 req/s with errors) · 2–4 workers before the node cache (unstable) · 80 % CPU per machine (−25 % throughput) · DeepFilterNet-style denoising gate (−0.19 dB) · a userspace L4 proxy in front of the gateway (−25 %). Every one is written up with its numbers in the repository.

04 / COLLABORATE

Where the next measurement should come from

  1. A real backend. Replace the mock with llama.cpp or Petals on real machines and re-run the load test.
  2. The control-plane migration. Move users and audit into the same store as tokens, then re-test two and four workers with the pooled adapter that already exists.
  3. A second host. Everything here is single-host; a two-host fleet would test whether dispatch latency and fairness degrade as predicted.
  4. Router hardening. The adversarial bucket is 50.75 % — a small classifier over the attached document would likely fix it.
