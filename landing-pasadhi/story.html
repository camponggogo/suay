The build log, told as a story

Six measurements that turned
a room of PCs into a pool

Every step below changed the architecture because a number said so. The failed ideas are kept in the repository, because they are the part that saves the next team a week.

2026-10-19

Fifty machines, one Python process

The first real load test. Throughput sat at 12 req/s while latency grew linearly; at C=50, 96.5 % of the response time was queueing above a 174 ms floor. The fleet was fine — the control path was the bottleneck.

12.0 req/s · p50 3 811 ms
2026-10-20

Split the planes and the fleet wakes up

Heartbeats moved out of the gateway into a node plane: state in memory, one batch flush every ten seconds, sharded by crc32. Heartbeat throughput tripled and single-request latency halved.

44 → 161 req/s per shard
2026-10-21

The ceiling was the event loop

A raw health endpoint served 58.7–71.2 req/s while a completion cost about 60 ms of loop time. Caching the live node list for five seconds took the same workload from 4.9 to 15.0 req/s; a second worker added another 48 %.

15.7 → 22.3 / 24.8 req/s
2026-10-21

Stop computing the same tokens twice

Content-addressed 256-token blocks, a registry of which machine holds which block, and longest-prefix routing. The median collapsed by 157×; p95 did not move at all.

111.4 s → 0.71 s (157×)
2026-10-21

Specialists beat one big generalist

A router that reads the question and the attached document sends work to the right expert: 90.15 % over 6 000 queries. Eight 1B experts fit in 32 machines where a mixture needed 86.

90.15 % · 31.5 µs
2026-10-22 → 23

One office, one group, one web

Groups of 100–200 machines share 30 % under a single id with an elected controller, working offline for internal jobs. Mixed fleets add small GPUs: 1 450 cards reach 9.54 PFLOPS f32, and the price follows measured impact, not a flat rate.

3 564 GFLOP/s · 30 links
